## 三、关键端到端验证（非组件测试）

任务书要求「桌面功能须进行真人可操作的 Windows 验收，不能只用组件测试代替」，
并要求提醒、窗口、备份等形成可验证闭环。以下为实机验证记录。

### 3.1 提醒调度（`tools/verify_reminders.py`）

| 场景 | 预期 | 实测结果 | 判定 |
| --- | --- | --- | --- |
| 5 秒后到期 | 发出并写入 `fired_at` | `fired_at=2026-09-23T03:35:26.124Z` | ✅ 不漏发 |
| 2 小时后到期 | 不发出 | `fired_at=None` | ✅ 不提前打扰 |
| 30 小时前（超 6h 补发窗） | 标记为过期 | `fired_at='expired'` | ✅ 可见地作废，非静默丢弃 |

**日志证据**（系统通知确实发出）：

```
[2026-09-23][04:11:41][lumen_lib::reminders][INFO] 发出提醒 be7982a6-...：
    任务「AITODO-DEDUP 去重验证」，计划时刻 2026-09-23T03:39:25.347Z
[2026-09-23][04:11:41][lumen_lib::reminders][INFO] 通知已提交给 Windows 通知中心（提醒 be7982a6-...）
```

**去重验证**（`tools/verify_dedup.py`）：插入一条"刚刚到期"的提醒，
等待第 1 个 tick 后 `fired_at = 2026-09-23T03:35:56.135Z`；
再等约 2 个 tick（70 秒）后复查，**该值完全未变**。判定 ✅ 不会重复轰炸。

### 3.2 窗口能力（Win32 API 读取，非界面自述）

| 窗口 | 可见 | `WS_EX_TOPMOST` | `WS_EX_TRANSPARENT` | `WS_EX_TOOLWINDOW` |
| --- | --- | --- | --- | --- |
| `Lumen 今日`（悬浮窗） | 是 | **是** | 否 | **是**（不在任务栏/Alt+Tab） |
| `Lumen`（主窗口） | 是 | 否 | 否 | 否 |

与配置 `floatingAlwaysOnTop=true`、`floatingClickThrough=false`、
`floatingShowInTaskbar=false`、`mainAlwaysOnTop=false` **逐项一致**。
判定 ✅ 置顶、穿透、任务栏显隐是真实的窗口级生效。

### 3.3 窗口安全恢复（`tools/verify_window.py`）

### 3.7 §5 重复任务验收例（自动化，`recurrence_e2e.rs`）

完整跑通任务书给出的验收序列，并在**模拟重启后**逐项校验：

1. 创建周一/三/五重复任务（起点 2026-09-21）→ 断言首次三次发生日期正确
2. 完成周一那次 → 断言 `completed_at` 已写入、其它发生不受影响
3. 单独改周三标题 → 断言标记为 `exception`、`occurrence_key` **未变**
4. 从下周一"此次及以后"改规则 → 断言新增 1 个分段
5. 校验历史 → 断言已完成的周一仍是 `done` 且完成时间保留；周三的例外标题未被冲掉
6. 跳过周五那次 → 断言实例软删除 + 跳过记录存在 + 系列其它发生仍在
7. 修改整个系列的优先级 → 断言未完成实例同步为 3、**已完成历史不变**
8. 模拟重启 → 断言完成状态、例外、分段、跳过记录全部仍在，
   且不存在重复的 `(series_id, occurrence_key)`

判定 ✅ 任务书 §5 的验收例完全通过。

## 四、开发过程中发现并修复的真实缺陷

**这部分比"全部通过"更有价值。** 以下缺陷均由测试或实机验证发现，
其中若干是"不报错但会静默出错"的类型。

| # | 缺陷 | 影响 | 发现方式 | 修复 |
| --- | --- | --- | --- | --- |
| 1 | **`DAILY` 的 `INTERVAL` 完全未生效** | "每 3 天"实际变成每天，用户的重复规则静默错误 | `expands_daily_with_interval` 测试 | `date_matches` 对 Daily 改为按天数取模 |
| 2 | **嵌套 tokio 运行时导致启动崩溃**（exit 101） | 应用直接无法启动 | 实机启动（单测无法发现） | 托盘菜单不再查库，改用 AppState 内存缓存 |
| 3 | **物化起点取错** | 起点已过去的重复系列会少生成实例 | 端到端验收测试 | 改用首个发生时刻为基准 |
| 4 | **本地日期时间解析不兼容空格分隔** | `NaiveDateTime::to_string()` 产物无法被自己解析，物化必然失败 | 修复 #5 让错误暴露后 | 解析同时接受 `T` 与空格分隔 |
| 5 | **静默吞掉物化失败**（`.unwrap_or(0)`） | 用户看到"创建成功"却只有第一个实例，且不知道原因 | 代码审查 | 改为显式报错并记录日志 |
| 6 | **窗口标签取错字段**（`currentWindow` 应为 `currentWebview`） | 悬浮窗里显示整个主界面（不报错，只显示错东西） | 对照 Tauri API 源码 | 改用正确字段 |
| 7 | **`combineDateTime` 静默滚动非法日期** | `2026-13-45` 被滚成 `2027-02-14`，用户看到的日期与输入不符 | `datetime.test.ts` | 回读各分量要求完全一致 |
| 8 | **时间字符串宽度不一致** | 破坏字典序比较，排序与区间查询出错 | Rust 测试 | `validate_time` 统一归一化为 24 字符 |
| 9 | **`bucketOf` 把已完成任务判为逾期** | 污染用户对工作量的判断 | `datetime.test.ts` | 已完成任务不进逾期分支 |
| 10 | **BYSETPOS 规则序列化重复输出 `BYDAY`** | 往返后字段出现重复元素 | 往返测试 | 有 setpos 时不再输出 by_weekday |
| 11 | **`describe()` 分支顺序错误** | 丢失"第 3 个"关键信息，只说"每周五" | 描述文案测试 | 先判断 setpos |
| 12 | **"整个系列"改优先级时跳过例外实例** | 用户改完整系列发现个别实例没变且找不到原因 | 验收例断言 | 例外只锁定用户改过的字段 |
| 13 | **`reqwest` / `keyring` feature 名错误** | 编译失败 | 编译 | 按 crates.io 实际 feature 列表修正 |
| 14 | **默认快捷键 `Ctrl+Alt+T` 被系统占用** | 有一个快捷键静默失效 | 实机日志 | 改为 `Ctrl+Alt+D`；同时验证了冲突提示有效 |
| 15 | **唯一约束冲突被误判** | `INSERT OR IGNORE` 掩盖真实错误 | 测试 | 显式检查 `rows_affected` |
| 16 | **`SELECT *` 新增列导致测试构造缺失字段** | 编译失败 | 编译 | 补齐测试构造 |

另外，开发过程中我自己的**测试断言也写错过两次**，都是先加诊断输出确认真实值，
再判断是代码错还是断言错：

- 改期测试：把 UTC 换算方向搞反，误以为代码有问题，实际是断言写错日期。
- 备份验证脚本：把辅助用例算进了计数，导致"周任务命中 2 条"的误报。

## 五、未解决问题（如实列出）

### 5.1 功能未实现

见 `docs/acceptance-checklist.md` 附二的完整清单（26 项）。要点：

- 账号与云同步（含服务端）
- 第三方任务导入（Todoist / Microsoft To Do / Google Tasks / Notion）
- PDF 导出、自动更新、首次启动引导、样例数据
- "极简模式"窗口、提醒声音、全局主题色、自定义背景
- 任务复制、列表内手动拖拽排序、项目合并入口
- 定时自动备份、应用内"清空全部数据"

### 5.2 平台限制

| 问题 | 原因 | 替代方案 |
| --- | --- | --- |
| 通知点击后无法跳转到任务 | `tauri-plugin-notification` 在桌面端不支持 Actions API（源码注释明确写 "action related options are ignored"） | 通知正文带任务标题；回到应用手动查看 |
| 透明度采用 CSS 而非整窗 alpha | 整窗 alpha 会连带降低文字对比度，难以保证可读性 | CSS `opacity` + 明暗主题自适应 |

### 5.3 验证缺口

| 缺口 | 风险 | 建议的验证方式 |
| --- | --- | --- |
| 干净环境（无开发工具）安装验证 | 可能缺少运行时依赖 | 在未装 Rust/Node 的 Windows 机器上运行安装包 |
| 真实 API Key 端到端调用 | 协议实现可能有细节偏差 | 需用户提供任一服务商的 Key 实测 |
| 多显示器断连后的窗口找回 | 窗口可能停留在已移除的显示器上 | 插拔外接显示器后检查；已有「把悬浮窗移回右下角」兜底 |
| 任务栏与托盘四种显隐组合枚举 | 组合行为可能不一致 | 逐一切换四种组合并重启验证 |
| 1000+ 条任务的性能 | 大数据量下可能卡顿 | 生成测试数据后测量列表/日历/搜索响应 |
| 文字对比度数值测量 | 半透明状态下可能不达 WCAG AA | 用对比度工具测量各主题下的关键文字 |

### 5.4 复现步骤（针对已修复缺陷）

供回归验证使用：

1. **DAILY INTERVAL**：新建重复任务 → 规则选"每 3 天" → 查看预览的接下来 4 次日期
   → 应为 21/24/27/30 而非连续的 21/22/23/24。
2. **启动崩溃**：启用托盘后启动应用 → 应正常启动并输出"系统托盘已就绪"，
   不出现 tokio panic。
3. **窗口安全恢复**：运行 `python tools/verify_window.py set-click-through`
   → 启动应用 → 运行 `python tools/verify_window.py check-recovered`
   → 穿透应为 False 且有"已穿透已在启动时关闭"的日志。
4. **静默日期滚动**：在编辑表单的计划日期填入非法值（如手工构造 `2026-13-45`）
   → 应被拒绝而不是被改成 2027 年。
5. **§5 验收例**：`cd src-tauri && cargo test recurrence_e2e -- --nocapture`。

## 七、结论

- 已实现功能的正确性有 **328 项自动化测试**（243 Rust + 85 前端）与
  6 类端到端实机验证支撑，关键闭环（提醒不漏发不重复、备份可往返、
  重复任务历史不丢、窗口可恢复）均有实测证据而非推断。
- 开发过程中发现并修复了 16 个真实缺陷，其中 5 个属于"不报错但会静默出错"
  的类型（DAILY INTERVAL 失效、日期静默滚动、窗口标签取错字段等），
  这类缺陷如果没有测试与实机验证很难被发现。
- **未完成项 26 项、验证缺口 6 项**已在
  `docs/acceptance-checklist.md` 中逐项列出。
  本报告不以"未发现 Bug"作为质量证明。

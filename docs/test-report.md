### 3.8 本轮新增能力的实机验收（`tools/verify_v020.py`，CDP 驱动真实界面）

**为什么不用 UI Automation**：Windows 的 UI Automation **看不到 WebView2
内部的元素**（实测只能枚举到 16 个外壳元素），所以"点某个按钮"这件事没法
用 UI Automation 做。这里改用 WebView2 自带的 Chromium 远程调试协议（CDP）：
给进程设置 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`，
就能连上每个窗口执行 JS、派发真实事件、读取真实 DOM。比"截图猜坐标"可靠，

### 3.9 悬浮窗按钮与"拖动调节"的实机验收（`tools/verify_floating.py`）

用户实机反馈"置顶/穿透/关闭点了没反应"。诊断分两步：

1. **后端有没有问题？** 用 `element.click()` 绕过 `mousedown` 直接派发 click，
   状态立刻从 `alwaysOnTop: true` 变成 `false`，且没有任何错误提示
   → 后端与权限都正常；
2. **那就是前端**：顶栏既是拖动区又放着按钮，`mousedown` 先触发
   `startDragging()` 开始拖窗口，`click` 永远不会发生。

因此这个脚本**必须用 CDP 的 `Input` 域派发真实鼠标按下/抬起**——
只发 click 是测不出这类缺陷的。验收项包括按钮、不透明度拖动、
尺寸调整后的布局检查、以及悬浮窗内的完整编辑保存。

「大小调节不能出显示 bug」被拆成可测量的断言：横向溢出为 0、
缩放手柄仍在窗口内、顶栏与底栏都可见，并在 260×200 与 1400×1800
两个极限尺寸上分别检查。

## 四、开发过程中发现并修复的真实缺陷

**这部分比"全部通过"更有价值。** 以下缺陷均由测试或实机验证发现，
其中若干是"不报错但会静默出错"的类型。

| # | 缺陷 | 影响 | 发现方式 | 修复 |
| --- | --- | --- | --- | --- |
| 1 | **`DAILY` 的 `INTERVAL` 完全未生效** | "每 3 天"实际变成每天，用户的重复规则静默错误 | `expands_daily_with_interval` 测试 | `date_matches` 对 Daily 改为按天数取模 |
| 2 | **嵌套 tokio 运行时导致启动崩溃**（exit 101） | 应用直接无法启动 | 实机启动（单测无法发现） | 托盘菜单不再查库，改用 AppState 内存缓存 |
| 3 | **物化起点取错** | 起点已过去的重复系列会少生成实例 | 端到端验收测试 | 改用首个发生时刻为基准 |
| 4 | **本地日期时间解析不兼容空格分隔** | `NaiveDateTime::to_string()` 产物无法被自己解析，物化必然失败 | 修复 #5 让错误暴露后 | 解析同时接受 `T` 与空格分隔 |
| 5 | **静默吞掉物化失败**（`.unwrap_or(0)`） | 用户看到"创建成功"却只有第一个实例，且不知道原因 | 代码审查 | 改为显式报错并记录日志 |
| 6 | **窗口标签取错字段**（`currentWindow` 应为 `currentWebview`） | 悬浮窗里显示整个主界面（不报错，只显示错东西） | 对照 Tauri API 源码 | 改用正确字段 |
| 7 | **`combineDateTime` 静默滚动非法日期** | `2026-13-45` 被滚成 `2027-02-14`，用户看到的日期与输入不符 | `datetime.test.ts` | 回读各分量要求完全一致 |
| 8 | **时间字符串宽度不一致** | 破坏字典序比较，排序与区间查询出错 | Rust 测试 | `validate_time` 统一归一化为 24 字符 |
| 9 | **`bucketOf` 把已完成任务判为逾期** | 污染用户对工作量的判断 | `datetime.test.ts` | 已完成任务不进逾期分支 |
| 10 | **BYSETPOS 规则序列化重复输出 `BYDAY`** | 往返后字段出现重复元素 | 往返测试 | 有 setpos 时不再输出 by_weekday |
| 11 | **`describe()` 分支顺序错误** | 丢失"第 3 个"关键信息，只说"每周五" | 描述文案测试 | 先判断 setpos |
| 12 | **"整个系列"改优先级时跳过例外实例** | 用户改完整系列发现个别实例没变且找不到原因 | 验收例断言 | 例外只锁定用户改过的字段 |
| 13 | **`reqwest` / `keyring` feature 名错误** | 编译失败 | 编译 | 按 crates.io 实际 feature 列表修正 |
| 14 | **默认快捷键 `Ctrl+Alt+T` 被系统占用** | 有一个快捷键静默失效 | 实机日志 | 改为 `Ctrl+Alt+D`；同时验证了冲突提示有效 |
| 15 | **唯一约束冲突被误判** | `INSERT OR IGNORE` 掩盖真实错误 | 测试 | 显式检查 `rows_affected` |
| 16 | **`SELECT *` 新增列导致测试构造缺失字段** | 编译失败 | 编译 | 补齐测试构造 |
| 17 | **全新数据库里创建第一条任务直接失败** | `sort_order` 是 REAL 列，但空表时 `COALESCE(MAX(sort_order), 0) + 1` 的求值结果被 SQLite 判成 INTEGER，sqlx 按 f64 解码即报 `SQL type INTEGER is not compatible with REAL`。**新装用户的第一次「新建任务」就会失败**，且报错文案与"新建"毫无关联 | 本轮新增的集成测试（`commands_e2e`）在空库上创建任务 | 查询加 `CAST(... AS REAL)`，并在注释里写明这个只会在空库上出现的坑 |
| 18 | **拖拽排序在"精度不足重新编号"后用过期坐标算位置** | 中点插入法把相邻差值对半砍到 <1e-6 时会触发重新编号，但旧代码仍用**重新编号前**的左右值算中点，结果可能把任务插到列表最前面 | 新增测试连续 60 次往同一位置插入 | 重新编号后**重新读取邻居**再算；两次仍分不开则显式报错而不是乱插 |
| 19 | **任务/项目/分类/标签/子任务的"保存"全部失败** | `QueryBuilder::separated()` 的 `Separated::push()` **本身就会写入分隔符**，因此 `sep.push("title = ").push_bind(v)` 生成的是 `title = , ?1`，SQLite 报 `near ",": syntax error`。这个写法在三个文件里出现 **52 次**，等于所有编辑功能都存不进去 | **用户在实机操作悬浮窗时截图报告**"改标题报数据库错误"；用 CDP 复现定位 | 全部改为 `push_bind_unseparated`，并补上"真的执行一次 UPDATE"的回归测试（此前只有校验函数的单测，SQL 从未被执行） |
| 20 | **悬浮窗顶栏的置顶/穿透/关闭按钮点了没反应** | 顶栏既是 `data-drag-region` 又放着按钮，`mousedown` 先触发 `startDragging()` 开始拖窗口，`click` 永远不会发生。后端其实完全正常（用 `element.click()` 绕过 mousedown 时状态立刻变化，已实测确认） | **用户实机反馈**"点关闭也没效果" | 起拖时显式排除 `button/input/select/textarea/a/[role=button]/[data-no-drag]`；验收脚本改用 CDP `Input` 域派发**真实鼠标按下/抬起**，专门防这类"只发 click 测不出来"的缺陷 |
| 21 | **导出的 PDF 是一张空白页**（1,076 字节） | 打印报告被渲染在 `.app` 容器**内部**，而导出时正是用 `body[data-print='on'] .app { display: none }` 隐藏主界面——报告跟着一起被隐藏，WebView2 打印"当前页面"自然什么都没有 | **用户导出后直接把文件发回来**："导出的 pdf 没有任何内容"；本机复现同样是 1 KB | 把报告移到 `.app` 的**兄弟节点**，并在代码里写明"报告不能放进 `.app`"的原因；验收脚本增加"文件小于 5 KB 就告警"的判断 |

另外，开发过程中我自己的**测试断言也写错过两次**，都是先加诊断输出确认真实值，
再判断是代码错还是断言错：

- 改期测试：把 UTC 换算方向搞反，误以为代码有问题，实际是断言写错日期。
- 备份验证脚本：把辅助用例算进了计数，导致"周任务命中 2 条"的误报。

## 五、未解决问题（如实列出）

### 5.1 功能未实现

见 `docs/acceptance-checklist.md` 附二的完整清单。要点：

- 账号与云同步（含服务端）——本轮明确不做
- 第三方任务导入（Todoist / Microsoft To Do / Google Tasks / Notion）
- 首次启动引导、样例数据
- "极简模式"窗口、提醒声音、全局主题色、自定义背景
- 定时自动备份、应用内"清空全部数据"

### 5.2 平台限制

| 问题 | 原因 | 替代方案 |
| --- | --- | --- |
| 点击系统通知无法跳转到对应任务 | 桌面端合成 toast 的**激活回调需要应用有打包身份（AUMID + COM 激活器）**，`tauri-plugin-notification` 在桌面端不提供 Actions/点击回调 | 提醒触发时在应用内弹出**可点击的提醒条**，点「打开任务」直接定位到该任务（本轮已实现，见 §3.8） |
| 透明度采用 CSS 而非整窗 alpha | 整窗 alpha 会连带降低文字对比度，难以保证可读性 | CSS `opacity` + 明暗主题自适应 |

### 5.3 验证缺口

| 缺口 | 风险 | 建议的验证方式 |
| --- | --- | --- |
| 干净环境（无开发工具）安装验证 | 可能缺少运行时依赖 | 在未装 Rust/Node 的 Windows 机器上运行安装包 |
| 真实 API Key 端到端调用 | 协议实现可能有细节偏差 | 需用户提供任一服务商的 Key 实测 |
| 多显示器断连后的窗口找回 | 窗口可能停留在已移除的显示器上 | 插拔外接显示器后检查；已有「把悬浮窗移回右下角」兜底 |
| 任务栏与托盘四种显隐组合枚举 | 组合行为可能不一致 | 逐一切换四种组合并重启验证 |
| 1000+ 条任务的性能 | 大数据量下可能卡顿 | 生成测试数据后测量列表/日历/搜索响应 |
| 文字对比度数值测量 | 半透明状态下可能不达 WCAG AA | 用对比度工具测量各主题下的关键文字 |

### 5.4 复现步骤（针对已修复缺陷）

供回归验证使用：

1. **DAILY INTERVAL**：新建重复任务 → 规则选"每 3 天" → 查看预览的接下来 4 次日期
   → 应为 21/24/27/30 而非连续的 21/22/23/24。
2. **启动崩溃**：启用托盘后启动应用 → 应正常启动并输出"系统托盘已就绪"，
   不出现 tokio panic。
3. **窗口安全恢复**：运行 `python tools/verify_window.py set-click-through`
   → 启动应用 → 运行 `python tools/verify_window.py check-recovered`
   → 穿透应为 False 且有"已穿透已在启动时关闭"的日志。
4. **静默日期滚动**：在编辑表单的计划日期填入非法值（如手工构造 `2026-13-45`）
   → 应被拒绝而不是被改成 2027 年。
5. **§5 验收例**：`cd src-tauri && cargo test recurrence_e2e -- --nocapture`。

## 七、结论

- 已实现功能的正确性有 **342 项自动化测试**（257 Rust + 85 前端）与
  8 类端到端实机验证支撑，关键闭环（提醒不漏发不重复、备份可往返、
  重复任务历史不丢、窗口可恢复、按钮真的可点）均有实测证据而非推断。
- 开发过程中发现并修复了 20 个真实缺陷，其中 7 个属于"不报错但会静默出错"
  或"看起来能用其实不能用"的类型（DAILY INTERVAL 失效、日期静默滚动、
  窗口标签取错字段、所有编辑保存失败、悬浮窗按钮点了没反应等）。
  其中 3 个是**本轮实机验收与用户反馈**才暴露的：单测覆盖不到的
  "SQL 从未被执行""按钮 mousedown 被拖拽抢走"这类问题。
- **未完成项 21 项、验证缺口 8 项**已在
  `docs/acceptance-checklist.md` 中逐项列出。
  本报告不以"未发现 Bug"作为质量证明。

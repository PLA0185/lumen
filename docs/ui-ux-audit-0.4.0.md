## 数据安全和交互结果

- 建立 `is_user_modified` 历史触碰标记和统一的重建安全判断。只有无用户改动、无附属数据、未完成且不在回收站的纯物化发生可硬删重建。附件副本、子任务、提醒、依赖、焦点、标签等数据会阻止删除；保留实例转为例外，保存结果会告知数量。
- 「删除此次及以后」使用 UTC occurrence key 作为包含该次的停止边界，浏览未来范围不会再生成。COUNT/UNTIL 仍受规则及系列结束字段约束。时区变更进入新分段，旧发生的 UTC 身份不被重新解释。
- 实机验收发现较新的「整个系列」规则会被旧未来分段重新覆盖。改为以规则版本覆盖其生效点之后的旧分段，并增加回归测试。预览按当前有效规则和新时区显示，正常界面只在折叠项中展示技术规则。
- 项目/分类合并与解除归属会同步系列模板；级联软删除会停止相关系列的未来生成。标签合并和删除会同步系列标签模板。
- 验收工具仅使用隔离 profile，成功后校验目标确属系统临时目录并重试删除；失败保留目录供排查。没有生产 profile 放行参数。

## 保留但未改的地方及原因

- Calendar、Board、Floating、Settings 已有明确的分页、数量提示或导航层级，本轮隔离桌面路径未发现需要立即推翻布局的阻断缺陷。密集内容的人工可读性仍需评估。
- TaskEditor 的链接、项目、分类、耗时、标签仍在主表单；这轮先折叠最低频且占高的区域，避免同时重排所有字段造成范围语义回归。
- `ScopeDialog` 仍承载单次内容编辑和删除范围；新规则编辑独立入口更符合「改安排」的心智模型。下一轮应测试用户能否在不看说明的情况下找到两个入口。

## 发布前未完成 / 未实测

1. 任务书要求的 16 步重复任务实机链路只覆盖了创建、规则预览、两个规则范围，以及既有单次编辑/删除；重启、维护、UI 添加并保留子任务/提醒/附件/依赖/副本的整链实测未完成。相关数据安全有 Rust 集成测试，但不能代替真实 UI。
2. Calendar、Stats、Organize、Dependency search、Floating、Focus 各视图的受控 `A 开始 → B 完成 → A 完成` 延迟测试未齐。已有 request gate 和部分分页延迟测试，仍不足以覆盖任务书矩阵。
3. AI 没有真实服务商密钥，无法证明真实生成预览后的范围说明与 Apply 体验；既有整改验收中四个 provider 均未配置，状态独立性无法区分。
4. 尚未逐项完成 100+ 今日任务、大回收站、大量项目/标签/依赖/报告的人工可用性评估；2,000 条规模脚本只验证了边界提示与检索。
5. 不升 `0.4.0`、不打 tag、不发布安装包。完成上述实机与交互检查后才能重新评估发布。

## 后续建议

- 先扩展隔离实机脚本，按任务书 16 步逐项验证，并在失败时保留证据。
- 为六个异步视图注入可控延迟，分别断言旧请求无法回写。
- 观察用户在 TaskEditor 中寻找「单次修改」与「修改规则」的路径，再决定是否合并入口。

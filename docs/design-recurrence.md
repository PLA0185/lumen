# 重复任务与数据结构设计说明

> 本文档对应任务书 §5「重复任务：必须作为独立核心模块实现」与 §12
> 「数据结构说明、迁移与同步策略、重复规则与例外的设计说明」。
>
> 实现位置：`src-tauri/src/recurrence.rs`（规则引擎）、
> `src-tauri/src/recurrence_service.rs`（持久化与范围语义）、
> `src-tauri/migrations/`（表结构）。

---

## 一、为什么不用现成的 RRULE 库

调研结论（`docs/api-research-rust-crates.md`）：`rrule` crate 已停更 17 个月，
且其月末处理策略是库内固定的，**无法按任务书要求"定义一致的处理策略并展示给用户"**。

因此本项目实现了一个聚焦的规则引擎，只覆盖任务书列出的规则类型，
但每条边界行为都是显式的、可测试的、可向用户解释的。

代价是规则类型有限（不支持 RRULE 的全部特性，如 `BYSETPOS` 配合多个月份、
`BYWEEKNO`、`BYYEARDAY` 等）。这是刻意的取舍：**可解释性优先于表达力**。

## 二、三层数据模型

```
task_series                规则 + 时区 + DTSTART + rule_version
  │
  ├── task_series_segments 规则分段：从某次起改用新规则 / 新字段（"此次及以后"）
  │
  ├── task_series_skips    单次跳过：该次不发生（"单次取消"）
  │
  └── tasks (series_id)    实例：真实任务记录
                           occurrence_kind = 'generated'（规则生成）
                                           | 'exception'（用户单独改过）
```

### 为什么"跳过"要独立一张表

任务书要求「单次取消显示为该次跳过，不意外取消整条系列」。

若复用 `tasks` 表加一个 `skipped` 状态：任务表里的每一行都会出现在列表、
日历、统计中，而"被跳过的那一次"是一段**不存在**的发生。把它当任务存储会导致
所有查询都要额外排除它，并且**污染统计分母**（任务书 §7 要求清楚标注分母）。

独立一张表语义清晰：跳过的发生既不是任务，也不是数据缺失。

## 三、稳定身份：`(series_id, occurrence_key)`

`occurrence_key` = 该次的**原始计划发生时间**（UTC ISO-8601 字符串）。

这条不变式是 §5 多项要求的实现基础：

| 任务书要求 | 如何由稳定身份满足 |
| --- | --- |
| 每次发生以"系列 ID + 原始计划发生时间/序号"取得稳定身份 | 身份就是这个二元组 |
| 即使用户把某次改到另一日，仍视为同一次 | 改期只改 `planned_at`，**不动** `occurrence_key` |
| 不能在旧日期再生成一个副本 | 数据库唯一索引 `idx_tasks_occurrence` 强制 |
| 规则分段后能准确判定实例归属 | 分段与跳过都用 `occurrence_key` 指认"是哪一次" |
| 完成/撤销完成只针对本次 | 直接改该实例行 |

数据库层的强制：

```sql
CREATE UNIQUE INDEX idx_tasks_occurrence
  ON tasks (series_id, occurrence_key)
  WHERE series_id IS NOT NULL AND occurrence_key IS NOT NULL;
```

有测试锁定这一点（`recurrence_e2e::acceptance_weekly_mon_wed_fri_full_lifecycle`
断言改期后 `occurrence_key` 不变，且重启后仍无重复）。

## 四、时间与时区的存储方式（§5 明确要求写入设计说明）

### 存储格式

- 所有时间戳一律以 **UTC ISO-8601 固定宽度字符串**存储：
  `YYYY-MM-DDTHH:MM:SS.sssZ`（24 字符）。
- 本地时区**仅用于展示与"今天/本周"归属计算**，不做持久化。

### 为什么用固定宽度字符串而不是时间戳整数

1. 长度一致时，**字符串字典序等价于时间序**，SQLite 无需时间类型即可正确排序与区间查询。
2. 备份与导出文件本身就是可读的。
3. 不会有整数精度或时区解释的歧义。

这条性质有测试锁定（`commands::tests::time_comparison_is_lexicographically_safe`），
并且在开发中确实抓到过一个真实缺陷：只认毫秒与不认毫秒的字符串混存会导致比较出错
（`'Z' > '.'`），因此 `validate_time` 统一经 `to_db_time` 归一化。

### 规则推进用"本地墙上时间"

`task_series` 存 `dtstart_local`（本地墙上时间）+ `tzid`，展开时按本地时间逐次推进，
再按 `tzid` 转 UTC。

**理由**：重复任务的语义是"每天/每周的那个墙上时刻"，而不是"每隔 86400 秒"。
跨夏令时时，墙上时刻保持不变才是用户期望的行为。

测试用 `America/New_York` 的 11 月回拨验证：墙上时刻稳定为 09:00，
而 UTC 偏移从 −4 变为 −5。

### 夏令时的确定性处理

| 情况 | 处理 |
| --- | --- |
| 本地时刻存在且唯一 | 直接转换 |
| 本地时刻重复（秋季回拨） | 取**最早**的那个 |
| 本地时刻不存在（春季跳变） | 按 UTC 解释，保证**不丢实例** |

未知 `tzid` 回退为 UTC 并记日志，不让一个陌生的时区标识让整个任务不可用。

## 五、边界策略（界面上会显示同样的说明）

| 情况 | 策略 |
| --- | --- |
| 每月 31 日，遇到只有 30 天的月份 | **跳过该月**（不挪到 30 日） |
| 每月 29/30/31 日，遇到 2 月 | **跳过**（闰年 2 月 29 日存在时正常发生） |
| 每年 2 月 29 日，平年 | **跳过**（只在闰年发生） |
| 第 5 个星期 X，该月不足 5 个 | **跳过该月** |

`RecurrenceRule::edge_policy_note()` 在规则涉及月末时返回这段说明，
前端在规则编辑器下方直接展示。有测试断言"涉及月末的规则必须给出说明，
且每日/每周规则不会打扰用户"。

### 死循环防护

"永远不可能发生"的规则（如每年 2 月 30 日）必须安全返回空结果而不是卡住。
实现用 `MAX_PROBE_DAYS = 366 × 40`（约 40 年）作为向前探测上限，
并有测试 `impossible_rule_terminates_with_empty_result` 锁定。

## 六、惰性展开

**绝不预先复制无限多的未来任务。**

`materialize_range(series_id, range_start, range_end, limit)`：

- 只落库**请求范围内**应当发生的实例；
- **已存在的实例一律不改动**——保护用户的完成记录与单独修改；
- 被跳过的发生不会创建实例；
- 分段规则按"该次落在哪一段"生效；
- 只创建 `occurrence_kind = 'generated'` 的实例。

物化起点取**首个发生时刻**而不是 `utc_now()`：`dtstart` 可能在过去
（用户补录一个已开始的习惯）也可能在未来（提前安排），以首个发生为基准两种情况都正确。
这个细节在开发中出过 bug——用 `utc_now()` 会让"起点已过"的系列少生成实例，
由端到端测试发现并修复。

创建系列时默认物化 90 天内的实例（可配置 1–730 天），单次上限 500 条。

## 七、范围语义（§5 强制要求的三选一）

### 仅此次

把该实例标记为 `occurrence_kind='exception'` 且 `is_exception=1`，写入新字段。
`occurrence_key` 保持不变。

**为什么必须标记为例外**：后续"此次及以后"重算规则时，例外实例会被跳过，
从而保证"用户单独改过的内容不会被冲掉"。

### 此次及以后

1. 在 `task_series_segments` 新增一条分段，起点为该次的 `occurrence_key`，
   记录新规则与字段覆盖；
2. `task_series.rule_version` 递增；
3. 删除该次之后**未改动且未完成**的旧实例：

```sql
DELETE FROM tasks
WHERE series_id = ?1 AND occurrence_key >= ?2
  AND occurrence_kind = 'generated'
  AND status <> 'done' AND completed_at IS NULL;
```

4. 按新规则重新物化未来实例。

**已完成实例与例外实例一律保留**——这是 §5「已完成实例、修改记录和历史
不能因改规则而消失」的实现。

### 整个系列

更新系列本身的规则与基础字段，并同步到实例。这里有一个需要澄清的语义：

> **例外只锁定用户真正改过的那个字段，其余字段仍跟随系列。**

于是：
- 改**标题**时跳过例外（保护用户的自定义标题）；
- 改**优先级、预计耗时、描述**时包含例外（它们是系列的共同属性）。

**理由**：用户在这一次上改了标题，说明"这次内容不一样"，但不代表
"这次的优先级永远不跟着系列走"。若把例外整体排除，用户改完整个系列的优先级后
会发现个别实例没变，而且找不到原因。这个语义由验收例中的断言发现并修正
（原实现整体排除例外）。

## 八、历史保护

`history_guard(series_id, cutoff_key, confirm)` 统计该次之前的已完成实例数。
若非零且调用方未显式确认，**直接拒绝操作并说明原因**：

```
此操作会影响 N 个已完成的历史任务
请先在界面上查看影响范围，确认后再执行（避免已完成记录被追改）
```

而不是默默改掉历史数据。

`EditScope` 与 `DeleteMode` 对未知取值直接报错：
**绝不静默按"整个系列"处理**——否则用户以为只改了一次，实际动了全部。

---

## 九、删除的三种范围

| 范围 | 行为 |
| --- | --- |
| 仅本次 | 写入跳过记录 + 软删除该实例；系列继续 |
| 此次及以后 | 软删除该次之后的未完成实例；系列结束条件改为"到该次为止" |
| 整个系列 | 实例全部软删除（可在回收站恢复）+ 删除系列记录 + 实例的 `series_id` 置空以免悬挂引用 |

## 十、数据表清单

| 表 | 用途 | 关键约束 |
| --- | --- | --- |
| `tasks` | 任务与重复实例 | `idx_tasks_occurrence` 唯一索引保证稳定身份 |
| `task_series` | 重复规则 | `rrule` + `tzid` + `dtstart_local` + `rule_version` |
| `task_series_segments` | 规则分段 | `UNIQUE (series_id, rule_version)` |
| `task_series_skips` | 单次跳过 | `UNIQUE (series_id, occurrence_key)` |

其它表（项目、分类、标签、子任务、依赖、提醒、附件、专注会话、设置、目标）
见 `src-tauri/migrations/0001_init.sql` 与后续迁移文件，
每个表在 SQL 注释里都写明了对应的任务书条款。

## 十一、迁移策略

- 迁移文件位于 `src-tauri/migrations/`，由 `sqlx::migrate!` 在编译期嵌入二进制；
- 启动时自动执行未应用的迁移；
- **迁移前自动复制数据库文件**到 `backups/pre-migrate-<时间戳>.db`；
- `app_meta.schema_version` 记录应用级版本（当前为 4）；
- 全部写操作走事务，避免"半条规则"。

| 版本 | 内容 |
| --- | --- |
| 0001 | 初始结构（14 表 + 索引 + 触发器） |
| 0002 | `task_series_skips`（单次跳过）+ occurrence 覆盖索引 |
| 0003 | `goals`（个人目标） |
| 0004 | `tasks.period_type`（周期跨度）+ 部分索引 |

实机验证：`tools/verify_db.py` 检查表、索引、触发器与迁移状态。

## 十二、同步策略（未实现）

任务书 §9 允许"可选择启用"账号与云同步。本轮按用户决定**不做同步**，
因此没有同步冲突策略。数据模型已预留两个字段以避免将来做破坏性迁移：

- `tasks.sync_rev INTEGER NOT NULL DEFAULT 0`
- `tasks.sync_state TEXT NOT NULL DEFAULT 'local'`

若将来实现同步，需要补充的设计至少包括：离线修改的合并规则、
重复系列的冲突解决（分段与跳过的合并语义）、删除的同步（软删除 vs 墓碑）、
附件同步策略。**这些均未设计，不应被视为已就绪。**

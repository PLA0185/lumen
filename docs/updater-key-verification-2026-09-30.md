# 自动更新地址与签名核验（2026-09-30）

## 实际结果

- GitHub `releases/latest/download/latest.json` 在本机可读取，最新 Release 和清单版本
  均为 **v0.4.0 / 0.4.0**，安装包使用匿名 Release 直链。v0.4.0 客户端不会将同版本
  视为新版；推送源代码不会自动产生更新安装包。
- `%USERPROFILE%\.tauri\lumen-updater.key` 与 DPAPI 密码文件存在，当前账户可以解密。
  这只能说明本机有可用于签名的凭据，不能说明它对应已安装程序的公钥。
- 使用 `tools/updater-secret.ps1 -Build` 实际生成安装包和签名后，Tauri 明确报告本机
  私钥与 `plugins.updater.pubkey` 不匹配。另用缓存的 `minisign-verify` 库，以配置中的
  原公钥验证实际安装包和 `.sig`，返回 **UnexpectedKeyId**，不是成功。
- 搜索本机用户目录、旧 `D:\Todo` 项目与仓库外备份中的 key / pub 文件，未找到匹配
  原公钥的 Lumen 私钥。目录枚举有一处 Windows 临时系统目录拒绝访问；没有声称扫描
  了所有磁盘或其他电脑。没有读取、输出或提交其他程序的私钥。

## 本轮采取的处理

保留程序现有公钥，未轮换密钥、未发布不兼容的 GitHub Release / 更新清单。
本地 NSIS 安装不依赖 updater `.sig`，所以本轮功能已手动安装到原程序目录。
使用 `/S /UPDATE` 跳过同版本安装的维护选择；最初仅 `/S` 虽退出 0，却未替换旧程序，
字节核验发现后重试，最终确认实际程序内容与构建一致，仅存在 Tauri 的 NSIS bundle 标记。
没有删除用户数据或使用卸载重装绕过安装。

每次升级前保留一致性 SQLite 快照、完整数据目录与旧可执行程序；正式迁移自身也创建
一致性快照。数据库与密钥不进入 GitHub。

## 仍需解决的条件

要让原公钥对应的程序继续接受自动更新，需要找回那把匹配的原私钥，再签名并发布
更高版本。另一条路线是用户明确决定一次性手动升级并迁移公钥，但这会改变旧签名链，
本轮没有采取。GitHub Actions Secrets 是否保存了匹配的密钥，本轮未验证，不能据本机
不匹配推断 CI 也不能签名。

`updater-secret.ps1 -Status` 当前检查存在、解密和明文残留，不做密码学公钥匹配验证。
发布前必须核对实际签名；不能把它返回 0 或“构建成功”当作更新链已经恢复的证据。

# 0.4.61 实际窗口排版整改

## 整改范围

本轮根据用户提供的六张截图处理实机窗口问题，覆盖今天页顶部栏、全局搜索、新建任务表单、月历任务密度、备忘工具栏和流程画布。目标是按实际可用宽度安排各组控件，让操作按钮、字段标签、输入框和内容各自拥有稳定的空间。

## 根因与改动

- **整个应用被内容撑出窗口**：桌面壳层使用隐式网格行，复杂页面的最小内容尺寸会把整列拉高。根应用改为视口高度，桌面网格显式使用 `minmax(0, 1fr)` 行和列；窗口框架固定，滚动交给内容面板。
- **顶部操作和搜索挤在一行**：窄窗口下标题单独占行，操作按钮可自然换行，搜索移到独立的全宽行，PDF 操作留在搜索右侧。断点使用主内容区容器宽度，而不是只看屏幕宽度。
- **新建任务字段标签错位**：日期、时间、快捷选择、优先级、周期和重复规则原来在同一个弹性横排中竞争宽度，清除日期按钮还会掉到无关位置。现在日期/时间与快捷日期成组，属性字段成另一组；输入框和选择框统一为标签在上、控件在下，并按新建面板的可用宽度切换布局。保留表单顶部和底部的添加按钮。
- **日历单元格塞入过多任务**：月格最多预览两项，并用“另有 N 项”说明其余数量；选中日期面板仍展示当天全部任务。空间不足时，该面板移到月历下方，足够宽时仍可并排。
- **备忘和流程工具栏缩小或溢出**：移除按容器宽度缩放整条工具栏的逻辑，操作文字保持原字号并按组换行。
- **流程画布控件遮住步骤**：搜索、缩放和添加步骤控件被安排在画布网格的独立区域，画布节点只在绘图区内显示。

## 截图中未能处理的内容

第四张图是一行 Excel 数据，其中多列显示 `#DIV/0!`。这张图没有包含工作簿或公式上下文；源码检查也未发现 Lumen 会生成该类 Excel 公式的导出路径。无法从截图安全判断各列应如何计算，所以本轮未修改用户表格或猜测公式。拿到原工作簿和对应公式后才能定位这项问题。

## 验收边界

- 使用本地 Vite 运行真实应用组件，在 940×720 窗口检查今天页、新建任务表单、月历、备忘和流程页面；确认窄表单中的日期/时间、快捷日期与任务属性分组，标签位于控件上方，月历保持选中日期面板。浏览器的应用 HTML 当前缩放为 75%，因此 940px 的视口对应约 1253px 的 CSS 布局宽度。
- 当前浏览器不在 Tauri 桌面程序内，任务/资料读取显示应用预期的原生环境提示，不能访问用户数据库。因此，浏览器检查没有验证真实任务数据下的月历折叠数量或流程节点与工具栏的覆盖关系。
- 未在 Windows 安装包中做完整人工操作；OnePlus Ace 2 / Android 16 也未实机安装验收。Android APK 会按用户的持续要求与 Windows 同版构建、发布，但构建成功不等于设备启动已验证。
